Tests that fix their own selectors

Hand-written UI tests on an enterprise CPQ app kept breaking whenever the markup shifted. I built a pipeline that records a flow, turns it into a readable BDD test, and repairs broken locators on its own.

Role
Built and demoed end to end
Stack
Playwright · Claude API · Cucumber-js · TypeScript
Status
Working proof of concept, demoed to my manager

The problem

The app under test is a GWT-based Salesforce CPQ front end. Generated markup and dynamic IDs mean a locator that worked last sprint can vanish in the next one. Every break meant someone opening the step file, finding the new element and patching it by hand.

Writing new BDD scenarios was slow too. Product could read Gherkin, but nobody wanted to write it for every flow.

The approach

  1. Record. Playwright codegen captures a real user flow in the browser.
  2. Generate. The recording goes to the Claude API, which writes a Gherkin feature file and matching Cucumber-js step definitions.
  3. Run. Cucumber-js executes the scenario against the app.
  4. Heal. When a step fails on a missing element, the pipeline saves a backup of the step file, captures the current DOM, asks for a replacement locator, patches the step and re-runs.
  5. Restore. If the healed run still fails, the backup is restored so a bad fix never sticks.

Architecture

Key code

// heal.ts (simplified)
export async function runWithHealing(feature: string) {
  const result = await runCucumber(feature);
  if (result.passed || !result.missingLocator) return result;

  const stepFile = result.failedStep.file;
  await backup(stepFile);                        // always reversible
  const dom = await captureDom(result.page);
  const fix = await suggestLocator(result.missingLocator, dom);

  await patchStep(stepFile, result.missingLocator, fix);
  const retry = await runCucumber(feature);
  if (!retry.passed) await restore(stepFile);        // bad fix never sticks
  return retry;
}

Results

  • Full loop working end to end: record, generate, run, heal, re-run.
  • Demoed to my manager on the real CPQ application.
  • Along the way, sorted out local environment and OneDrive sync problems that were breaking test runs.

What's next

  • Run it in CI and open a pull request with the locator diff instead of patching silently.
  • Add a confidence threshold so low-certainty fixes go to a human.
  • Prefer role and text locators over IDs when generating steps.

A matching engine that counts microseconds

PulseTrade is an order matching engine for a simulated equities exchange. It's my deep dive into the kind of low-latency, correctness-first systems that trading firms run.

Role
Solo build
Stack
Java 21 · Spring Boot · Kafka · Redis · PostgreSQL · JMH · Prometheus · Grafana
Target
25,000+ orders/sec on one node, p99 under 5 ms

The problem

An exchange has to be fast and fair at the same time. Every incoming order must match against the best opposite price, and orders at the same price must fill in the order they arrived. Get that wrong and you've built an unfair market. Get it slow and nobody uses it.

The approach

  1. Price-time priority. Each side of the book is a sorted map of price levels, and each level is a FIFO queue of orders.
  2. One matching thread. Matching stays single-threaded per symbol, so there are no locks on the hot path and the result is deterministic.
  3. Events out, not calls out. Every trade is published to Kafka. Persistence and metrics consume it without slowing the matcher.
  4. State and history. Redis holds a snapshot of the live book, and PostgreSQL stores trade history.
  5. Measure everything. JMH benchmarks for throughput and latency, Prometheus and Grafana for live metrics, and JUnit and integration tests on the matching invariants.

You can try the matching logic on this page: open the live order book ↗

Architecture

Key code

// OrderBook.java (simplified)
private final TreeMap<Long, ArrayDeque<Order>> asks = new TreeMap<>();
private final TreeMap<Long, ArrayDeque<Order>> bids = new TreeMap<>(Comparator.reverseOrder());

void matchBuy(Order in) {
  while (in.qty > 0 && !asks.isEmpty()) {
    var best = asks.firstEntry();                 // lowest ask
    if (in.isLimit() && best.getKey() > in.price) break;
    var queue = best.getValue();
    Order maker = queue.peekFirst();              // oldest at this price
    long fill = Math.min(in.qty, maker.qty);
    in.qty -= fill; maker.qty -= fill;
    events.publish(new Trade(maker.id, in.id, best.getKey(), fill));
    if (maker.qty == 0) queue.pollFirst();
    if (queue.isEmpty()) asks.pollFirstEntry();
  }
  if (in.qty > 0 && in.isLimit()) rest(bids, in);
}

Where it stands

  • Started in September 2026. Core book and matching logic first, then events, persistence and benchmarks.
  • The 25,000 orders/sec and sub-5 ms p99 figures are targets I'm building toward and will publish JMH results for, not claims yet.

What's next

  • Publish JMH numbers and a latency histogram.
  • Add order cancel and replace, and an LMAX-style ring buffer experiment.
  • Replay a day of synthetic market data and compare against the targets.

A running coach that learns from your runs

RunCoach is a React Native app that tracks runs with live GPS, syncs with Apple Health and Google Fit, and generates training plans from how you actually run, not from a template.

Role
Design and build
Stack
React Native · HealthKit · Google Fit · Node.js
Links
GitHub repo ↗

The problem

Most free plans hand you the same 12-week schedule whatever your fitness. As someone who runs and organises a run club, I wanted plans that react to the runs you've actually logged.

The approach

  1. Track. Live GPS route, distance, pace and time while you run.
  2. Sync. Pull past workouts from HealthKit on iOS and Google Fit on Android so the app knows your history from day one.
  3. Plan. Generate the next week from recent volume and pace instead of a fixed template.

Architecture

Key code

// pace.ts (simplified): live pace from GPS points
export function paceMinPerKm(points: Point[], windowSec = 30) {
  const now = points.at(-1)!.t;
  const recent = points.filter(p => now - p.t <= windowSec * 1000);
  let meters = 0;
  for (let i = 1; i < recent.length; i++) meters += haversine(recent[i - 1], recent[i]);
  const minutes = (now - recent[0].t) / 60000;
  return meters > 0 ? minutes / (meters / 1000) : null;   // smooths GPS jitter
}
